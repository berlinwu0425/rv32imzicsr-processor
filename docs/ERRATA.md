# 勘誤表（Errata）

本表更正 [docs/report.pdf](report.pdf) 中已知的錯誤。報告 PDF 維持提交時的版本不再修改，以本表為準。

最後更新：2026-10-16

---

## 1. baseline CPU 在安全邊界上的位置（摘要、4.6、4.11 圖八、5.2、第六章）

**原文**：Theorem A1（flush 觸發下一拍即完成清除）對應 F = 0；真實 baseline CPU（D = 0, F = 0）座落於安全區內側。

**更正**：baseline 應為 **(D, F) = (0, 1)**，**恰位於邊界 F = D + 1 上**，而非安全區內側。

**理由**：在 `speculative_boundary_model.v` 中，`age` 自分支解決那拍（第 0 拍）起算，`flush_active = (age >= F)` 與 `instr_at_launch = (age == D + 1)` 在同一拍比較。因此 F 的意義是「管線自第 F 拍起為清空狀態」，與危險指令「於第 D + 1 拍抵達啟動級」使用同一套計數。

- **D = 0**：`vec_start` 由 EX 級訊號驅動（`cpu_top.v`），分支也在 EX 解決，L = R = EX。危險指令於第 1 拍抵達啟動級，與 Ghost Timing Model 的結果一致。
- **F = 1**：ID/EX 為同步清除（`id_ex_register.v`：`if (!rst_n || flush)`）。第 0 拍管線尚未清空，第 1 拍才是清空狀態（Theorem A1）。

報告原本把時脈邊緣造成的「+1」只計入危險指令的抵達時間，沒有計入 flush 的生效時間，因而誤將 A1 對應為 F = 0。

**baseline 仍然安全**：危險指令抵達與 flush 生效發生在同一拍，屬於邊界上的等號情況。同一時脈邊緣上，ID/EX 暫存器的 flush 優先於 stall 與一般更新，危險指令不會被 latch 進啟動級；Theorem A2（flush 後下一拍 `vec_start` 恆為假）證明了這一點（於鏡像模型上）。

**影響**：
- **baseline 對 flush 延遲沒有餘裕。** flush 路徑若增加任何一拍延遲（例如為時序收斂將 flush 訊號暫存一級），即會越過邊界，產生推測性污染。
- **第 4.4 節「同一 cycle 內 flush 優先」**：在抽象模型中原為一項定義；對 baseline 而言，它是安全成立的關鍵前提，並由 RTL 的暫存器寫法與 Theorem A2 支持。
- **第 5.2 節第 3 點**：原文「kill/commit 對這顆處理器目前而言並非燃眉之急，對更接近邊界的未來擴充，其必要性會提高」應修正為：baseline 已在邊界上，任何會增加 flush 延遲的設計修改，都需要 kill/commit 或等效的保護機制。
- **圖八**：藍點應位於 (D, F) = (0, 1)，即基準線 F = D + 1 上。

## 2. 第 4.8 節：掃描組數

**原文**：涵蓋 D ∈ {0, 1, …, 8}、F ∈ {0, 1, …, 10}、S ∈ {0, 1, 2, 3}，共 384 組獨立驗證。

**更正**：應為 **396 組**（9 × 11 × 4）。提交時缺少 D ∈ {0, 1}、F ∈ {6, 7}、S ∈ {0, 1, 2} 的 12 組，已於 2026-10-16 補跑，結果皆與邊界公式一致。三組邊界掃描合計 **792 組**（99 + 297 + 396）。

## 3. 圖八：安全區標註

**原文**：Safe（相對觀察一基準線，經 20 組獨立形式化驗證支持）

**更正**：應為 **99 組**（第 4.6 節，D 0–8 × F 0–10）。

## 4. 第 4.7 節：「safety 與 liveness 安全區完全重合」（補充說明）

在 `speculative_equivalence_model.v` 中，kill 訊號只在誤判時發出，正確路徑的指令不會被 kill，因此 liveness 在此模型中結構上必然成立，兩者安全區重合是模型設計的直接結果。報告中「kill/commit 只要維持正確性就不會犧牲進度」的推論在本模型設定下成立，但不宜推廣為一般性結論。
